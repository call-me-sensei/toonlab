# Commercial Procedural-Tree Reference Study

This note records the implementation-level conclusions from the private
commercial reference library. The purchased `.blend`,
textures, thumbnails, extracted node data, and per-preset values remain
gitignored and are not redistributed.

## Inventory and scope

- 400 asset presets across 17 named cohorts.
- Broadleaf coverage: oak, birch, maple, ash, ginkgo, bonsai, and stylized
  variants.
- Conifer coverage: pine, spruce, and stylized variants.
- The library is useful evidence for recursive woody and conifer controls. It
  does not provide suitable reference engines for bamboo colonies, palms,
  cycads, tree ferns, pseudostems, specialized mangrove roots, rosette trees,
  or cacti.

The private extraction reports and inspection tools remain alongside the
gitignored local reference library; no vendor identifiers or paths enter
Toonlab's public runtime, API, presets, or shipped documentation.

The controlled multi-seed/development audit and the implementation technique map
are documented in
`docs/research/commercial-woody-engine-audit.md`. Its private aggregate
measurements can be regenerated with the local, gitignored inspection tools.

## Reusable algorithm ideas

The Toonlab implementation now has two deliberately separate layers:

1. `woody-baseline-v1` evaluates the licensed procedural graph directly through
   Blender. A gitignored adapter contains source-specific object and socket
   identifiers. Tree Lab and the public recipe surface use only Toonlab names.
2. Toonlab's semantic JavaScript plant graph remains the editable runtime for
   Doodle Tree, architecture-specific engines, semantic LODs, and browser-only
   fallback. It is the layer we can modify freely for game-specific behavior.

The following relationships are carried from the licensed baseline into the
Toonlab recipe adapter:

1. A bounded spawn interval for branches on each parent axis.
2. Separate length, radius, and child-count decay by axis generation.
3. A configurable branching exponent rather than one global scale ratio.
4. Even phyllotactic distribution with controlled biological jitter.
5. Separate low-frequency trunk deviation and higher-frequency branch noise.
6. Endpoint growth response so branches do not remain rigid rays.
7. Architecture-specific crown envelopes.
8. Leaf/organ attachment beginning at a selected axis generation.
9. Conifer whorl spacing and multiple secondary sprays along each main branch.
10. Geometry resolution kept independent from structural growth parameters.

The licensed graph is the visual/behavioral baseline for its supported woody
and conifer cohorts. Toonlab does not expose its source identifiers, materials,
textures, UI names, or files through the public package. Generated geometry is
re-materialized with Toonlab-owned bark and foliage materials.

The same evaluated graph now emits LOD0–LOD3 in one source-file load. Each
level has a deterministic structural/detail profile, separate Toonlab
structure and foliage primitives, a per-level geometry report, and a grounded
closed trunk/root base. Tree Lab requests these exact levels rather than
switching back to the older compatibility generator during LOD inspection.

## Explicit non-adoptions

- Flowers and reproductive geometry remain outside Tree Catalog v3.
- The reference library's simple root displacement is not used for specialized roots.
  ToonLab retains semantic modules for buttress, prop, aerial,
  pneumatophore, knee, fibrous, rhizome, coralloid, and shallow-radial roots.
- Non-woody engines retain architecture-specific topology. A palm is not
  generated by forcing a woody recursion into a tall trunk, and bamboo is not
  a narrow broadleaf tree.
- A vendor preset is not botanical validation. Every ToonLab species remains
  disabled until all five stages pass front, side, and back comparison against
  the local botanical reference archive.

## Current verification policy

The reference cohorts are useful for parameter ergonomics and silhouette
variation, not for proving exact species fidelity. The public support gate
therefore remains:

- deterministic graph and stable structural hash;
- architecture-specific topology checks;
- semantic LOD/export checks;
- local reference image provenance;
- manual front/side/back morphology approval for all five stages.
